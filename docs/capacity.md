# Shared-backend capacity trial

On 2026-10-26, the release Docker stack handled **2,000 simultaneous 2×2 matches,
4,000 WebSocket connections, and 100 legal moves/second** with zero request or
stream-delivery errors in a 60-second measured run. PostgreSQL alone was sufficient
for coordination and event delivery in these trials.

| Matches | Sockets | Offered moves/s | Accepted moves | HTTP p95 | Both players p95 | Both players p99 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 100 | 200 | 20 | 300 | 5.52 ms | 5.79 ms | 6.95 ms |
| 1,000 | 2,000 | 50 | 3,000 | 6.15 ms | 6.52 ms | 8.91 ms |
| 2,000 | 4,000 | 100 | 6,000 | 6.18 ms | 6.59 ms | 9.03 ms |

The 100-match run lasted 15 seconds. The larger runs lasted 60 seconds each.
“Both players” measures from sending a move until its committed event has arrived
on both actual WebSockets. Each run received every expected sequence. Command
routing split exactly 50/50 between the Rust replicas. No match finished during
the measured periods.

The 1,000-match run warmed up 24 legal plies per match, then added 3 measured
plies each. The 2,000-match run did the same. All sockets remained open throughout
the measured period. Creating, connecting and warming the matches took 40.4 and
92.4 seconds respectively, with at most 32 setups running concurrently. The small
run warmed up 12 plies. Moves were generated by the real Rust rules engine;
there were no fake servers or engine bots in the workload.

## CPU and memory

Docker stats were sampled every five seconds. CPU percentages use **100% = one
CPU core**, not the whole host. Memory is Docker's reported working usage, not a
measurement of the host's total RAM requirement.

| Container | 1,000 matches: average CPU | Peak memory | 2,000 matches: average CPU | Peak memory |
| --- | ---: | ---: | ---: | ---: |
| Rust A | 3.7% | 140.0 MiB | 8.3% | 281.1 MiB |
| Rust B | 4.5% | 148.4 MiB | 8.3% | 279.8 MiB |
| PostgreSQL | 13.6% | 247.8 MiB | 28.6% | 268.7 MiB |
| HAProxy | 2.5% | 33.4 MiB | 4.4% | 54.6 MiB |

These numbers cover the measured phase. The 2,000-match setup averaged 127% CPU
in PostgreSQL and peaked at 298.3 MiB. Each Rust replica was limited to 1 CPU /
384 MiB, PostgreSQL to 2 CPUs / 768 MiB, and HAProxy to 0.5 CPU / 64 MiB. At 2,000
matches, the proxy is fairly close to its configured memory ceiling; raise the
limit and remeasure before increasing connection counts.

The host was an x86-64 AMD Ryzen 9 5950X with 32 logical CPUs. Containers had CPU
quotas, not dedicated cores; the load generator ran on the same host. Requests
used localhost HTTP without TLS or WAN latency. Rust used the release profile.
The database was PostgreSQL 18.6 with a persistent Docker volume.

## Limit discovered and fixed

The first 1,000-match ramp failed before the measured phase because an app reached
its inherited **1,024-descriptor soft limit**. A ticket request timed out; HAProxy
logged a readiness timeout with 1,019 sessions assigned to that replica. CPU and
memory were below their limits.

Compose now sets app/proxy soft and hard `nofile` limits to 65,536. Both subsequent
larger trials passed. The failed trial's resource samples are retained alongside
the successful results.

## Recovery and client checks

The real Compose checks passed with no sticky sessions:

- Conflicting moves commit once; retries return the original event.
- Streams catch up after PostgreSQL LISTEN connections are terminated.
- Hard-stopping either Rust replica preserves sessions, moves, and running clocks.
- Restarting all Rust replicas preserves the same checkpoint and clock deadline.
- PostgreSQL stop/start preserves committed matches and restores event delivery.
- Static assets remain available while the database is stopped.
- With PostgreSQL stopped, a browser reload and a Fairy-Stockfish reply succeeded
  with no API requests; local two-player routing was also checked in the browser.
- A real SQLite version 2 export imported successfully. Its PostgreSQL backup
  restored into a fresh database with the expected 2 accounts, 2 matches, and
  11 events.

There are 95 passing Rust contract/integration tests and 71 passing JS/WASM tests.
The server tests require real PostgreSQL. Provider credentials, cloud deployment,
and signed physical-device releases were outside this trial.

## Limits of the result

This is a short capacity check of early classical 2×2 positions, not a saturation
test or a cloud guarantee. It does not measure long matches, sustained database
growth, 4×4/8×8 workloads, TLS, abuse traffic, or cloud storage/network behavior.
Checkpoints include repetition state and replay history, so their size and write
cost grow with game length. Repeat the test with representative long games before
promising the same throughput there.

A single host still has a single failure domain. Use off-host backups and test
restores. Multiple stateless Rust replicas support rolling restarts and later
multi-host deployment; PostgreSQL remains the shared primary.

## Reproduce

Start the stack following [server.md](server.md). Use a disposable Compose project:
the checks stop/restart services, and the load generator creates real guest
accounts and leaves real games in its database.

```sh
node scripts/check-compose.mjs http://localhost:8080 nested-chess
cargo build --release --locked -p nested-chess-server --example capacity
node scripts/measure-capacity.mjs http://localhost:8080 1000 60 50 24 32 claude/20261026_shared-backend/new-trial.json nested-chess
```

The load generator exits on the first request or stream error. The wrapper records
container resource samples beside the result. It requires Docker and a locally
built release executable.
