Online play: scope and cost

100 simultaneous human games looks feasible on a small Rust server. I would use a 4 GB AWS Lightsail VM, SQLite, and Google, GitHub, and Microsoft login. Budget about $30–40/month for the service and backups. The hard work is reliable multiplayer and account handling; validating chess moves is cheap.

Proposal, not an implemented backend. Prices checked 25 October 2026, USD, selected US regions, no tax or promotional credits. One server, without automatic failover. Server-side bots and spectators are excluded from the base estimate.

What changes

The existing Rust crate already validates moves, routes turns, scores boards, and saves/replays matches. The deployed app is a browser client on GitHub Pages; a new backend would own online games.

Server authority applies to online games. Local and bot games run on the device without login or a connection to the multiplayer backend.

I recommend one initial rated pool for human classical 2×2, with other settings available through casual invites and bot games unrated. More rated queues split a small player population. The existing evaluation worker should be disabled during rated games; that does not prevent external engine assistance.

Login providers and Rust libraries

openidconnect covers the OIDC flow for Google and Microsoft. Configure Microsoft for personal and work/school accounts, with tenant-aware issuer validation.

GitHub user login uses OAuth 2.0. Use the related oauth2 crate and GET /user to obtain its stable numeric account ID. Repository permissions are unnecessary for login.

Share the login, callback, and application-session flow across small provider adapters. Store OIDC issuer + subject or GitHub provider + numeric ID. Link another identity from an already authenticated account; matching emails alone never merge users. Match history and ratings belong to the internal user.

Server shape

Browser UI + WASM  ↔  Rust / Axum  ↔  SQLite on persistent disk
                         │
                 Google / GitHub / Microsoft

TLS and static assets share the app's origin.

One Rust process can own 100 matches and their socket connections. Use a serialized command queue per game and a bounded SQLite writer. Axum supports WebSockets; SQLite WAL permits concurrent readers with one writer.

  1. The client submits {request_id, expected_seq, board, uci}. The session identifies the user; the server checks their seat, turn, and current sequence.
  2. Validate against a candidate clone of the Rust game. Commit the event and new game sequence in one database transaction, then swap the cached game and broadcast. A failed commit leaves the accepted position unchanged.
  3. A retry with the same request ID returns the recorded result. A sequence gap triggers resync. Reconnect loads the persisted log; clients never submit an authoritative result or arbitrary position.
  4. When a match finishes, store its result and both rating changes exactly once in one transaction. Rebuild a lost cache from the log after restart.

Use an event sequence independent of chess ply: resignations and other match actions can change state without moving a piece. The current save loader replays its history; saving its JSON does not create a fast native checkpoint.

Data and client boundaries

Small tables: users; provider identities; sessions; games; ordered game events; ratings; rating changes. Enforce unique provider identity, username, game sequence, request ID within a game, and rating change per player/game. The server controls these writes.

The current UI directly owns its WASM game and local saves. Patching online checks into every handler is quicker initially. I recommend extracting a small session interface for local/bot/remote play instead: it makes turn permissions, undo/import availability, and reconnection explicit without rewriting the renderer. Allow roughly 1–2 extra development days for that separation.

Player clocks belong to the whole match. A disconnect should not automatically concede a game; reconnect while its clock runs. Server outages need an explicit pause/abort policy. These are proposed online rules, not changes to the existing offline game.

My choice: AWS Lightsail at roughly $30–40/month initially. The bundled disk and traffic make the bill predictable. Run SQLite on that VM with tested off-machine backups. Moving to managed PostgreSQL buys operational convenience and easier multiple-server deployment, at additional cost and coordination work; 100 player-versus-player games do not yet justify that structure.

Managed-container alternative

A Rust container plus managed PostgreSQL and a managed identity provider reduces VM maintenance. It also needs shared match ownership and delivery across instances. Cloud Run supports WebSockets, but open sockets keep an instance active and billed; connections time out and must reconnect, and affinity is best-effort. That architecture deserves its own database and always-active compute budget. The VM estimates above do not apply to it.

The continuous-occupancy model adds about 13.5 GB of uncompressed event storage each month. An 80 GB disk would fill within months after allowing for the OS and backup workspace. Compact completed replays or expand storage; the initial bill is not a promise of unlimited history at that price.

Continuous server-side Fairy-Stockfish games are a separate workload. Keep solo bots in the browser as today; otherwise budget and benchmark an engine-worker pool separately. A human match only needs the native rules engine.

Ratings and implementation order

Start everyone on an arbitrary common scale, such as 1500. A simple Elo update uses expected = 1 / (1 + 10^((opponent − player) / 400)) and new = old + K × (result − expected). I would start with K = 32 for both players and mark their first 20 rated matches provisional. This is a rating within this game, with no conversion to chess.com or FIDE Elo.

Elo does not supply calibrated uncertainty. Keep immutable results and rating algorithm versions so ratings can be recomputed. Whole matches remain the rating unit regardless of any future algorithm change.
